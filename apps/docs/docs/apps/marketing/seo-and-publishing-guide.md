# Marketing SEO and Publishing Guide

## What this feature does

The Marketing app publishes crawlable product pages and mobility articles. It
adds page-specific titles/descriptions, canonical URLs, social sharing
metadata, structured data, a sitemap and an RSS feed. These are generated by
Astro from the page source and build environment; there is no search-engine
runtime service in the Marketing app.

## Metadata path

1. A page passes metadata and optional structured data to
   `BaseLayout.astro`.
2. `BaseLayout` forwards page metadata to `SeoHead.astro` and combines shared
   Organization/WebSite schema with page schema.
3. `SeoHead` emits the document title, description, canonical, robots,
   Open Graph/Twitter cards, region, manifest, RSS and favicon links.
4. The SEO postbuild script scans generated HTML/XML and reports failures.

`SeoHead` uses a supplied canonical or derives one from `Astro.url.pathname`,
removing a trailing slash except for the root. The current pages generally
pass explicit `https://www.adhocx.com` canonicals. The layout de-duplicates
exact JSON-LD nodes and at most one Organization, LocalBusiness,
BreadcrumbList and WebSite node; it strips HowTo nodes. Page-level schema
types vary by route (for example BlogPosting and FAQPage).

## Search and syndication routes

| Route/source | Generation behavior | Important boundaries |
|---|---|---|
| `/sitemap.xml` — `src/pages/sitemap.xml.ts` | Generates XML from top-level `.astro` page modules, excluding `404.astro` and `delete-account.astro`, then adds article slugs from local `ARTICLES_CONTENT`. Includes `lastmod`, `changefreq` and priority. | Does not query the blog API; remote-only slugs may not appear in the sitemap. RSS is not included. |
| `/rss.xml` — `src/pages/rss.xml.ts` | Starts with local articles; during generation it requests up to 20 published blog posts with a 1.2-second timeout, merges results by slug, and emits RSS 2.0 XML. | Fetch errors fall back to seeded data. Since output is static, the feed is not refreshed until another build. |
| `/blogs/[slug]` — `src/pages/blogs/[slug].astro` | `getStaticPaths()` starts with source article slugs, requests up to 50 published backend posts with a 5-second timeout and adds nonduplicate slugs. Markdown-like content is converted to simple HTML during the build. | API unavailability falls back to local pages; remote posts not returned during build are not generated in that artifact. |
| `/404`, `/delete-account` | Both pages set `noindex`; the sitemap also excludes them. | The deletion route is still a static information page; it does not submit a delete request. |

The article-detail JSON-LD currently uses fixed `datePublished`,
`dateModified`, `wordCount` and `timeRequired` values rather than deriving all
of those fields from each article record. Page title and description are
clipped from article content, while the article metadata and images are
assembled in the Astro template.

## Build-time API configuration

The blog detail and RSS source checks `API_URL`, then `PUBLIC_API_URL`, then
defaults to `http://localhost:7001/api/v1`. Those requests happen during
static generation. Production builds that need current backend articles must
provide a reachable API origin at build time. A successful build alone does
not establish that an API was reachable or that the generated site contains
the intended current articles.

The site config declares `site: 'https://www.adhocx.com'`, static output,
no trailing slash, and `build.format: 'file'`. `@astrojs/sitemap` is present
in the package manifest but not wired in the Astro config; the explicit
TypeScript sitemap route is the implementation.

## Automated output checks

`npm run build` runs `astro build`, followed by the package `postbuild` script
`node scripts/seo-check.mjs`. The script scans generated HTML and checks:

- Unique 20–60 character titles for indexable pages.
- 70–165 character descriptions.
- Absolute canonical URLs on the declared site origin and matching generated
  page URLs.
- One H1 per page, Open Graph image, and image alt attributes.
- JSON-LD parseability and duplicate/deprecated schema checks.
- Sitemap origin, duplicates, trailing slashes and whether listed pages are
  indexable generated pages.
- `robots.txt` sitemap reference and presence of `llms.txt`.

The script logs errors but only exits nonzero for those findings when
`SEO_STRICT=1`. Thus “SEO check passed” means the script completed under the
current setting; it does not prove that search engines indexed pages, that
metadata is factually correct, or that a deployed origin serves the same
artifact.

In the Phase 11 build, the SEO check passed and reported seven warnings for
generated blog cover images without explicit width/height attributes. These
are layout-shift cautions, not build failures.

## Hosting and static asset configuration

| File | Configured behavior |
|---|---|
| `astro.config.mjs` | Static output; enables the Vercel static adapter when `VERCEL` is set. |
| `vercel.json` | Build command/output directory, clean URLs, cache headers for assets/images, and basic response headers. |
| `wrangler.jsonc` | Cloudflare static asset directory `./dist`, custom domains for apex and `www`, and observability setting. |
| `Dockerfile` | Builds the workspace with pnpm, copies `dist` into Nginx, serves files with an HTML fallback, exposes `/healthz`, and declares an Nginx health check. |

These are source configurations for possible targets; no deployment or
production environment was inspected in this phase.

## External content and claims

Marketing pages, blog content, JSON-LD descriptions and FAQ answers are
maintained as source text or build-time API content. Public statements about
SLAs, safety controls, fleet guarantees, performance, legal compliance or
company details should be treated as published claims—not evidence of a
verified operational integration. Reconcile such statements with the
responsible product, legal, security and operations owners before relying on
them.

No analytics tags/event implementation or cookie-consent component was found
in the audited `src/` tree. Earlier campaign specifications are not proof
that these capabilities are active.
